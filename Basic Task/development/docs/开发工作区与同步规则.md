## 二、⭐ 规则

### 1. 改代码只在 `development/` 里改

不要"改 Windows 副本 → 拷进仓库"。
**直接在仓库里编辑，改完 `git add` + `git commit`。**

### 2. 如果确实需要一份 Windows 侧副本用于阅读/编辑

**方向只能是仓库 → Windows 副本**，而且要在提交之后做：

```bash
# 从仓库同步到 Windows 副本（单向！）
rsync -a --delete \
  "$HOME/antlab/ANTLab-Infra-Tasks/Basic Task/development/" \
  /mnt/d/ANTLab_Agent/development-mirror/
```

**⚠️ 绝对不要反向拷（Windows 副本 → 仓库）。** 那会把旧内容覆盖上去，
而且因为副本缺文件、内容过期，覆盖是**静默**的 —— 提交信息里也看不出来。

### 3. 提交前必做：确认改动范围符合预期

```bash
cd ~/antlab/ANTLab-Infra-Tasks
git diff --stat              # 看改了哪些文件、改了多少行
git diff -- <可疑文件>        # 对每个文件确认改动是【你想改的】
```

**这次就是这么栽的**：那次提交的 message 只写了"补 _说明 里的一段话"，
但 `git diff --stat` 其实显示 **30 行改动**（整个文件被换掉了）。
**message 和实际改动不一致时，先看 `--stat`。**

### 4. 路径改动后跑审计

```bash
cd "Basic Task/development/src"
python3 tools/audit_all_paths.py      # 读取类 + 写入类路径 + 野生目录
python3 tools/inventory_writes.py     # 列出所有落盘/破坏性操作
```

两个工具都会**明确区分"真问题"和"允许不存在"**，
并且会报出它们**自己**的假阳性原因（这俩工具都踩过坑）。

## 四、怎么发现"文件被整体覆盖"

三个信号，任何一个出现都要停下来查：

| 信号 | 怎么看出来 |
|---|---|
| **`git diff --stat` 的行数远大于预期** | 只想改 3 行，却显示 30 行 |
| **提交 message 提到的文件 ≠ 实际改动的文件** | message 说"只改注释"，实际动了数据 |
| **运行行为与预期不符** | 比如注册表显示 ctx=16384，但你记得是 32768 |

**第 3 个是最晚暴露的** —— 这次是靠"审计路径时发现默认值不对"才顺藤摸瓜查到的。
