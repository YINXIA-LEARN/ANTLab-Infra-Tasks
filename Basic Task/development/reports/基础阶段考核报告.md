## 1. 项目与应用场景

### 1.1 服务对象

一个 **8 人规模的小型工作室**。工作室同时承担两类工作：

- **办公文档处理**：项目会议与进度资料的整理、客户进展邮件的撰写、内部管理制度的条款查询、入职与例外条件清单。
- **辅助编程**：读一段既有 Python 程序做问题定位与最小复现、按数据结构约定修复统计逻辑与边界处理。

### 1.2 需求构成：纯提示词 4 / 办公文档 4 / 编程 2

规定任务共 10 个，按 `src/common/tasks.py` 的 `kind` 字段（**权威定义**）分成三类：

| kind | 任务编号 | 数量 | 占比 | 输入里带不带文件 |
| --- | --- | --- | --- | --- |
| `prompt` 纯提示词 | P01–P04 | 4 | 40% | 不带 |
| `doc` 办公文档 | D01–D04 | 4 | 40% | 带 `办公输入01/02-*.md` |
| `code` 编程 | C01–C02 | 2 | 20% | 带 `编程输入03-ticket_stats.py` |

**4 : 4 : 2** —— 办公类（纯提示词 + 文档）合计 8 个，是编程类的 4 倍。
这与工作室的真实工作分布一致：日常绝大多数请求是"读资料、写文档、答制度"，编程任务是少数但要求更高（要能跑起来）。

> 出处：`src/common/tasks.py`（`TASKS` 列表的 `kind` 字段）、`results/<运行编号>/prompt-index.json`（逐任务的 `kind` 与文件）。

### 1.3 请求特点

| 特点 | 实测值 | 出处 |
| --- | --- | --- |
| 输入长度跨度大 | **152 ~ 2313 token**（最短 P01，最长 D01） | `results/<运行编号>/prompt-index.json` |
| 输出上限 | **2048 token**（`max_tokens`），任务自带"写完整程序"的要求 | `results/<运行编号>/run-config.json` |
| 并发 | 最多 **10 个同时到达**（8 人工作室，偶尔有人一次发两条） | `results/<运行编号>/run-config.json` 的 `concurrency: [1, 4, 10]` |
| 到达方式 | 一波同时发出（wave），不是泊松到达 | `src/bench/client.py` 的 wave 调度 |
| 采样 | `temperature = 0.0`（同一输入应得到稳定输出） | `results/<运行编号>/run-config.json` |
| 顺序 | `order = "shuffled"`，`seed = 20261009`（顺序可复现） | 同上 |

**关键矛盾**：单个请求的输入最长 2313 token，但输出**可能顶到 2048 上限**（长文档摘要、完整程序）。
所以"够不够用"这件事要同时看 **上下文容量** 与 **输出上限** 两个上限 —— 本阶段只优化了前者，后者暴露的问题见 §8。

### 1.4 优化目标

在 **8 GB 显存（RTX 5060 Laptop，实测 8151 MiB）** 这一硬约束下，让服务在 8 人工作室内可用：

1. **显存必须留有余量** —— 演示、浏览器、系统本身都要占显存，服务不能把卡吃满。
2. **单并发延迟要低** —— 交互式使用，首字延迟（TTFT）决定"手感"。
3. **多并发下不能雪崩** —— 10 个请求同时到达时，TTFT 会因排队抬升，需要确认抬升幅度是否可接受。
4. **输出质量要够用** —— 办公任务要能正确仲裁文档里前后矛盾的版本；编程任务给出的代码至少要能编译。

优先级：**先保证显存装得下且稳定，再谈延迟与吞吐**。因此本阶段的优化实验围绕两个旋钮展开：
**上下文容量（16384 → 32768）** 与 **KV 精度（f16/f16 → q8_0/q8_0）**，并在两个模型（0.6B / 1.7B）上各做一遍。

### 2.4 KV 配置总容量、每 slot 可用容量与分配方式

> 这一节是最容易写错的地方：`-c` 是**共享池总量**，不是"每槽值"。

| 口径 | 值 | 怎么得到 |
| --- | --- | --- |
| **分配方式** | **共享池**（`kv_unified = true`） | 启动日志 `load_model: initializing, n_slots = 4, n_ctx_slot = 32768, kv_unified = 'true'` |
| **配置总容量** | `-c` = **16384** 或 **32768 token** | 启动参数 |
| **各 slot 可用容量** | **动态**：4 槽全忙时最少约 **8192**（= 32768 ÷ 4）；只有 1 个请求时最多可用满 **32768** | 池总量 ÷ 同时在跑的请求数 |
| **实测可用容量** | **32698 token**（单请求独占池时的最大可接受输入） | 容量探测实测，`results/kv-capacity-probe.txt` |
| **KV 精度** | `f16`（默认）或 `q8_0` | 进程命令行 `-ctk` / `-ctv` |
| **KV 位置** | `CUDA0`（全部层） | 日志 `llama_kv_cache: layer N: dev = CUDA0` |
| **KV 实占显存** | **3584.00 MiB @ ctx 32768 / f16** → 折合 **112 KiB/token** | 日志 `llama_kv_cache: CUDA0 KV buffer size = 3584.00 MiB` |

**为什么确定是共享池而不是"每槽各一份"**：
`3584 MiB ÷ 32768 token ≈ 112 KiB/token`，只够**一个** 32768 的池；
若真是 4 槽各 32768，需要约 `14336 MiB`，而整卡只有 8151 MiB —— 不可能。

**这一条现在有直接实验证据了（不再只是日志推算）**：
一次专门的容量探测（单请求逐档加大输入、再二分收紧）实测出
**可接受的最大单请求输入 = 32698 token**，与配置总容量 **32768 只差 70 token**。
若真是"每槽 8192"，单请求在 8192 附近就该被拒 —— 实测却在 32698 才被拒。
**这直接证实了"单请求独占时能用满整个池"**，即共享池模型。

| 探测项 | 结果 | 出处 |
| --- | --- | --- |
| 环境 | Qwen3-0.6B-Q8_0 / `-c 32768` / KV f16/f16 / 4 slot 共享池 | `results/kv-capacity-probe.txt` |
| 方法 | 单请求逐档加大输入，观察服务是否返回 400；到边界后二分收紧 | 同上 |
| 逐档结果 | 1500 字→961 tok ✅；6000 字→3804 tok ✅；12000 字→7593 tok ✅；24000 字→15172 tok ✅；36000 字→22751 tok ✅；48000 字→30330 tok ✅；**60000 字→HTTP 400**（`request (37909 tokens) exceeds the available context size (32768 tokens)`） | 同上 |
| 二分收紧 | 51000 字→32225 tok ✅；**51750 字→32698 tok ✅（实测可接受的最大单请求输入）**；51937 字→❌ 超限；52125 字→❌ 超限 | 同上 |
| 超限行为 | **HTTP 400**，响应里附带提示可增大 `-c` | 同上 |
| 探测时显存 | **5549 / 8151 MiB** | 同上 |

**⚠️ 这个实测值的适用范围（必须一起引用）**：
探测只发**一个**请求，量到的是"**独占池**"的上限。
**并发时会摊薄** —— 4 个请求同时在跑时每个请求实际能用的额度约 8192，
10 个请求时约 3277。所以 **32698 这个数不能读成"并发下每个请求也能用这么多"**。
两者是这个池的两端：**独占上限 32698（实测）** 与 **摊薄后的动态额度（推算）**。

**那 70 token 的差额是留给输出的**：探测时输出上限设的是 `max_tokens=16`，
剩下的差额就是模板开销与少量余量 —— 说明**容量控制是准的**，不是"差不多能塞下"。

**⚠️ 一行容易误读的日志**：`n_ctx_slot = 32768` 是**池的标称值**，不是"每个 slot 能拿到 32768"。
`src/serve.sh status` 早期版本曾把它打印成"每槽 ctx=32768"，**已修正**。

### 2.6 模型选择、任务表现、上下文容量与显存之间的关系

- **为什么从 0.6B 开始**：8 GB 显存要同时装下权重、KV 池、计算缓冲，并给系统留余量。
  0.6B/Q8_0 的权重只占约 604 MiB（日志 `CUDA0 model buffer size`），剩下几乎全部留给 KV 池 —— 这是能把上下文做到 32K 的前提。
- **为什么也要测 1.7B**：参数量上去后，办公任务的条款引用与事实完整性明显更好（见 §8：
  D03 条款漏项从 0.6B 的 5/9 次降到 1.7B 的 1/9 次以内），但代价是显存与延迟同时变差（§7）。
- **上下文容量 ↔ 显存的关系（本机实测线性关系）**：KV 精度 f16 时约 **112 KiB/token**。

  | 配置 | KV 池理论显存 | 实测"加载后占用" | 出处 |
  | --- | --- | --- | --- |
  | ctx 16384 / f16 / 0.6B | ≈ 1792 MiB | 3648 MiB（含权重 604 + 计算缓冲） | `ctx16k-f16-06b-r1` |
  | ctx 32768 / f16 / 0.6B | ≈ 3584 MiB | 5490 MiB | `ctx32k-f16-06b-r1` |
  | ctx 16384 / q8_0 / 0.6B | ≈ 896 MiB | 2882 MiB | `ctx16k-q80-06b-r1` |
  | ctx 32768 / f16 / 1.7B | ≈ 3584 MiB | 6576 MiB | `ctx32k-f16-17b-r1` |

  **结论**：在 8151 MiB 的卡上，1.7B + 32K + f16 已经用到 6576 MiB（约 81%），
  余量只剩约 1.5 GB —— **这已经是本机可用的上限**，再往上加上下文或换更大模型会顶到显存墙。
  0.6B + 32K + f16（5490 MiB，约 67%）留有余量，是更稳的默认选择。

│  性能测试程序  tests/core/run_bench.py │

**两个服务是独立的**：控制层只管 Web 与代理，llama-server 只管推理。

### 3.3 输入组织、请求调用、测试统计、文件存储、前端展示、服务管理

- **输入组织**（`src/common/file_input.py`）：系统消息（逐字照抄题目"建议统一使用"的那段）+
  资料文件内容 + 任务提示词，用 `===== 资料区/任务区 =====` 分隔。
  组装后把每一段的 token 数单独算出来，和"服务端实测输入 token"对账
  （`run.log` 里可见例：`组装 D01: 本地分段合计 2296 token，服务端实测输入 2313（模板开销 17）`）。
  分段的合计值与服务端值**不相等**是预期的 —— 差额是 chat 模板开销，程序把它单独记为 `template_overhead`。
- **请求调用**（`src/bench/client.py`）：直接对 `http://127.0.0.1:8080/v1/chat/completions` 发流式请求，
  客户端计时（`t_submit` / `t_first` / `t_done`），并处理取消、超时、服务消失等异常路径。
- **测试统计**（`tests/core/run_bench.py`）：三段式（冷启动 → 预热 → 正式），
  正式阶段按 `并发档 × 轮次` 展开成 wave；结束时把中位数 / P95 / 吞吐 / 显存峰值写进 `summary.json`。
- **文件存储**：`results/<运行编号>/`，一次运行一个目录，**绝不覆盖**（编号带时间戳）。
  同时更新派生索引 `results/runs.json`（该文件是索引不是权威，见 §12.4）。
- **前端展示**（`src/web/`）：四个页面**全部实现**
  （`src/web/index.html` 第 51–54 行：`data-tab="chat" | "bench" | "results" | "service"`）。
  结果页有 5 个视图：汇总 / 逐请求 / 错误 / 配置 / **对比**；
  服务页有：两个服务的状态与启停、**测试期间自动重启的开关与参数**、**服务事件时间线**。
- **服务管理**：`src/serve.sh`（命令行）与网页服务页（图形）**两条路径共用**
  `control/model_manager.py` 的启停逻辑 —— 不重写第二份，避免"谁启动的"导致配置不一致。

### 3.4 一处重要的架构决定：配置与运行时状态分开

| 文件 | 进 git | 放什么 |
| --- | --- | --- |
| `configs/models.json` | ✅ | 模型**定义**（有哪些模型、怎么启动、SHA256）+ `default_active` |
| `.runtime/active-model.json` | ❌（`.gitignore` 覆盖） | **此刻正在用哪个模型** |

拆开的原因：把"配置"和"运行时状态"混在一个被 git 跟踪的文件里，
每切一次模型提交历史就脏一次。拆开后注册表永远干净，切换仍然持久化。

## 5. 指标与测试方法

### 5.1 指标定义与公式

所有时间由**客户端**采集（`src/bench/client.py`），起点是请求提交、终点是最后一个数据块到达，
**包含排队时间与网络传输**（这正是"用户实际感受到的延迟"）。

| 指标 | 定义与公式 | 说明 |
| --- | --- | --- |
| **TTFT**（首 token 时间） | `ttft_ms = (t_first − t_submit) × 1000` | 含排队 + 前缀计算 + 首 token 生成 + 传输 |
| **TPOT**（每 token 时间） | `tpot_excl_first_ms = (t_done − t_first) / (output_tokens − 1) × 1000` | **排除首 token**；分母是"输出 token 数 − 1"，因为首 token 的时间已经算在 TTFT 里 |
| **吞吐** | `output_tokens_per_s = Σ output_tokens / 墙钟窗口秒数` | **分母用实测墙钟时间**（从该并发档第一个 wave 开始到最后一个 wave 结束），**不用逐请求相对时间戳推算** —— 后者会低估窗口长度，曾把吞吐高估约 12 倍 |
| **完成耗时** | `total_ms = (t_done − t_submit) × 1000` | 整条请求的端到端时间 |
| **P95** | 线性插值分位数（另写一套算法，见 `tests/_testlib.py`） | 与 `summary.json` 的 P95 独立重算并对比 |
| **成功率** | `n_success / n_requests` | 分母是**该档的请求总数**（含失败、中断、被截断与被取消的）；**只有自然跑完（`finish_reason=stop` 或流里出现 `[DONE]`）才计入成功** |
| **显存峰值** | 运行期 `nvidia-smi` 采样最大值 | `summary.json → formal.<并发>.vram_peak_mib`，原始序列在 `gpu-samples-c<N>.csv` |

**两种 TPOT 口径都要记录**（`tpot_excl_first_ms` 与 `tpot_incl_first_ms`），两者必须不同，
否则说明有一处算错 —— `tests/core/test_03_metrics.py` 对此有断言。

### 5.2 时间采集位置与 token 统计

| 项 | 位置 / 来源 |
| --- | --- |
| 时间采集 | 客户端进程内 `time.time()`，三个时刻：提交 / 首块 / 结束 |
| 输出 token 数 | **服务端 `usage`** 或 `timings.predicted_n`（逐请求记录里用 `output_tokens_source` 标明实际用了哪个） |
| 输入 token 数 | **服务端 `usage.prompt_tokens`**（`prompt_tokens_source: "usage"`） |
| 服务端实际计算量 | `prompt_n_computed`（本次真正参与计算的 token 数，未命中前缀缓存的部分） |
| 前缀缓存命中 | `cache_hit_tokens` |
| 恒等式校验 | `prompt_n_computed + cache_hit_tokens == prompt_tokens`（服务端恒等式，`tests/core/test_02` 断言） |

**⚠️ 绝不按"流式块数"统计 token。** `tests/core/test_02_token_counting.py` 在真实记录上实测：

```
块数 == token 数 :   0 条      ← 从不相等的边界，证明这个边界真实存在
块数 <  token 数 :  81 条      （一个数据块含多个 token）
块数 >  token 数 :   9 条      （token 跨多块 / 含空块）
按块统计会偏 +2.2%
```

出处：`tests/README.md` §四"test_02 抓到的实测数字"。

### 5.3 预热、重复次数

| 项 | 做法 | 出处 |
| --- | --- | --- |
| 冷启动 | 服务刚加载完、前缀缓存为空时的**第一次**请求，单独记为 `cold_start`（1 条对象） | `summary.json → cold_start` |
| 预热 | 正式测试前跑 P01 让前缀缓存热起来 | `summary.json → warmup` |
| 正式 | 按并发档 × 轮次展开 | `summary.json → formal.<并发>` |
| 分段记录 | **冷启动 / 预热 / 正式三段分开记录，不混入正式统计** | `summary.json → warmup_note: "冷启动与预热单独记录，不混入正式测试统计（题目要求）"` |

**实测值**（9 次运行的 `cold_start.ttft_ms` 与 `warmup[0].ttft_ms`）：

| 运行编号 | 冷启动 TTFT | 预热后 TTFT |
| --- | --- | --- |
| ctx16k-f16-06b-r1-20261016-222516 | 22.95 ms | 10.9 ms |
| ctx16k-f16-06b-r2-20261016-224117 | 19.81 ms | 11.7 ms |
| ctx16k-f16-17b-r1-20261016-224726 | 25.04 ms | 17.0 ms |
| ctx16k-q80-06b-r1-20261016-223609 | 25.44 ms | 11.2 ms |
| ctx16k-q80-06b-r2-20261016-232040 | 22.64 ms | 11.6 ms |
| ctx16k-q80-06b-r3-20261016-232906 | 24.98 ms | 10.7 ms |
| ctx16k-q80-17b-r1-20261016-230952 | 29.30 ms | 18.0 ms |
| ctx32k-f16-06b-r1-20261016-223012 | 22.48 ms | 12.2 ms |
| ctx32k-f16-17b-r1-20261016-225813 | 25.41 ms | 16.4 ms |

**结论：冷启动 TTFT 约 20~29 ms，预热后约 11~18 ms**，即预热把首字延迟降低约 30~45%。
（出处：各运行 `summary.json` 的 `cold_start.ttft_ms` 与 `warmup[*].ttft_ms`。）

**✅ 一处口径差异（已查清，不是缺陷）**：`run-config.json` 里 `warmup.n = 2`，
但 9 次运行的 `summary.json → warmup` 数组**都只落了 1 条记录**。

**原因是 `n` 的语义**——它指**「冷启动 + 预热」的总请求数**，不是「预热几条」。
`run_bench.py` 的循环是：

```python
for i in range(n):                                  # n = 2 → i = 0, 1
    r["phase"] = "cold_start" if i == 0 else "warmup"
```

第 1 条（`i=0`）记成 `cold_start`，其余 `n-1` 条才记成 `warmup`。
所以 `n=2` = **1 条冷启动 + 1 条预热**，数组里 1 条是**符合预期**的。

**核实证据**（`results/ctx16k-f16-06b-r1-20261016-222516/run.log`）：

```
[22:25:27] 冷启动 + 预热（任务 P01 × 2）…
[22:25:28]   冷启动 TTFT 23 ms，总耗时 720 ms
[22:25:29]   预热1 TTFT 11 ms          ← 仅此一条，与 n=2 一致
```

**本报告一律按 `summary.json` 的【实际记录（1 条）】引用，不假定 2 条。**

⚠️ 不过这个字段名**确实有歧义**（字面读像"预热 2 次"），且曾让人误以为
"预热漏跑了一次"。已做两件事：
① 在 `run_bench.py` 该处补了注释说明语义，并把日志文案改成
「冷启动 + 预热（任务 P01 × 2，**含冷启动那一条**）…」；
② 建议后续把字段拆成 `cold_start_n` / `warmup_n` 两个名字。
**行为本身没有问题**——每轮都确实做了冷启动+预热，正式统计的隔离是成立的。

**重复次数**：档内 3 轮（`rounds: 3`）；整轮重复只对 `0.6B / 16K / f16` 做了 1 次（r1、r2）。
**其余每个配置只有 1 次整轮测量 —— 不足以做统计显著性判断**（见 §7.4）。

### 5.4 失败、取消和重试的处理

单条请求的状态由 `src/bench/client.py` 分成 **8 类**，语义互不重叠：

| 状态 | 含义 | 是否算成功 |
| --- | --- | --- |
| `success` | 拿到 `finish_reason` 或流里出现过 `[DONE]`，自然跑完 | ✅ |
| `truncated` | **输出撞上 `max_tokens` 上限被硬截断**（输出残缺） | ❌ 但**不算失败** —— 是配置上限问题，不是服务问题 |
| `service_lost` | 请求过程中**模型服务消失**（探测 `/health` 不可达） | ❌ |
| `incomplete` | 流在结束标记前断了，**但服务还在**（例如服务端中止了批次 / KV 溢出 `send_error`） | ❌ |
| `cancelled` | **我们主动停的**（测试被停止，或代码放弃这一条） | ❌ |
| `failed` | HTTP 错误（4xx/5xx）或别的连接问题 | ❌ |
| `timeout` | 超过 `timeout_s`（900 秒）未完成 | ❌ |
| `harness_error` | **测试程序自身的 bug**（不是模型问题） | ❌ |

**`service_lost` 与 `cancelled` 的区别是最容易混的一对**：
前者是"**服务**没了"，后者是"**我们**主动停的"。这个区分直接决定 §9 的恢复逻辑能否成立
（只有 `service_lost` 才应该触发自动重启）。

**⚠️ 关于"有上限的重试"**：题目点名要求围绕"服务退出和有上限的重试"设计边界样例。
**有上限的重试这一功能本阶段未实现**，因此也没有对应的测试与数据。

### 5.5 KV 容量指标的口径

题目要求"以 token 为单位区分配置总容量、各 slot 可用容量和实测可用容量"。
本阶段的口径与三个数的取值见 **§2.4**，此处只强调三件事：

1. **配置总容量** = `-c` = 16384 或 32768 token（启动参数）。
2. **各 slot 可用容量**是**动态**的（共享池），不是固定值：单请求可占满全池，4 槽全忙时约 8192。
3. **实测可用容量已有实测值**：在 `-c 32768` 下，**单请求最大可接受输入 = 32698 token**
   （探测方法：单请求逐档加大输入 → HTTP 400，再二分收紧；`results/kv-capacity-probe.txt`）。
   它与配置总容量只差 **70 token**，**这正是"共享池"的直接实验证据**。
   **适用范围**：该值只对"单请求独占"成立；并发时额度按池总量摊薄（4 并发约 8192、10 并发约 3277）。

**容量验证的测试边界与现象**：

| 项 | 值 |
| --- | --- |
| 超限表现 | **HTTP 400**，报 `request (37909 tokens) exceeds the available context size (32768 tokens)` |
| 服务端行为 | **拒绝该请求，服务不崩、不影响其他请求**（不是 `incomplete`，也不是 `service_lost`） |
| 本批 9 次运行是否触过这个边界 | **没有** —— 最长的输入是 D01 的 2313 token，距离 32768 的池还有大量余量 |
| 因此 | `ctx16k-q80-06b-r2` 那轮的失败**与容量无关**（是服务被杀，见 §9） |
| 探测时显存 | 5549 / 8151 MiB |

**输入与已生成 token 的计数方式**：`prompt_tokens` 来自服务端 `usage`（已生成部分按实际输出块累计），
`cache_hit_tokens` 与 `prompt_n_computed` 由服务端 `timings` 给出，三者满足恒等式（§5.2）。

### 6.2 基线的主要瓶颈

1. **并发到 10 时 TTFT 塌陷**：0.6B·16K·f16 从 c1 的 24 ms 涨到 c10 的 2352 ms（**约 98 倍**），
   TPOT 只从 6.31 ms 涨到 7.97 ms。**瓶颈是排队，不是单 token 生成速度**。
   证据：`summary.json` 里 c10 的 `throughput.window_s ≈ 49 s`，而 c10 的 30 条请求若串行执行按 TPOT 估算需要更久 ——
   说明服务端确实在并行处理，只是 slot 只有 4 个，10 个请求要排队。
2. **slot 数与并发档不匹配**：slot 默认 4，而并发档是 10。
   即 c10 档下 6 个请求在等 slot。这是 TTFT 塌陷的直接机制
   （`tests/core/test_04_concurrency.py` 对"并发 > slot 数时 TTFT 抬高"有断言）。
3. **KV 池吃掉大部分显存**：f16 + 32K 时 KV 池 3584 MiB，
   占整卡 8151 MiB 的 **44%**；加上 0.6B 权重 604 MiB 与计算缓冲，加载后就到 5490 MiB。
   这是"想提上下文就得付显存"的根源。

### 7.4 ⚠️ 重复测试的波动，以及为什么"单轮数据不能当结论"

**这是本节最要紧的一段。**

**（a）并发档的 TTFT 波动极大 —— c10 的 P95 常达中位数的 5~10 倍。**

| 运行编号 | c10 TTFT 中位数 | c10 TTFT P95 | P95 / 中位数 |
| --- | --- | --- | --- |
| ctx16k-f16-06b-r1-20261016-222516 | 2452 ms | 13842 ms | **5.6×** |
| ctx16k-f16-06b-r2-20261016-224117 | 2353 ms | 10384 ms | **4.4×** |
| ctx32k-f16-06b-r1-20261016-223012 | 1874 ms | 9902 ms | **5.3×** |
| ctx16k-q80-06b-r1-20261016-223609 | 2990 ms | 13797 ms | **4.6×** |
| ctx16k-f16-17b-r1-20261016-224726 | 4749 ms | 25352 ms | **5.3×** |
| ctx16k-q80-17b-r1-20261016-230952 | 2402 ms | **28053 ms** | **11.7×** |
| ctx32k-f16-17b-r1-20261016-225813 | 2377 ms | 23802 ms | **10.0×** |

出处：`results/report-data.txt` §二 的 `TTFT中位` 与 `TTFT-P95` 两列。

**含义**：c10 档里"快的那些请求"和"慢的那些请求"差了 5~12 倍。
只看中位数会以为"10 并发还行"，看 P95 会发现**有一批用户在等十几到二十几秒**。
因此本报告对 cv10 档的结论一律只说"**趋势**"，不下"定论"。

**（b）同一配置重跑一次（0.6B·16K·f16 的 r1 与 r2）的差异：**

| 指标（c10） | r1 | r2 | 差异 |
| --- | --- | --- | --- |
| TTFT 中位数 | 2452 ms | 2353 ms | −4.0% |
| TTFT P95 | 13842 ms | 10384 ms | **−25.0%** |
| 吞吐 | 419.1 tok/s | 390.3 tok/s | −6.9% |
| 成功率 | 29/30 | 30/30 | 1 条之差 |

**P95 在两次同样的配置下差了 25%** —— 这个量级说明：
**O1~O5 里所有小于 25% 的变化都需要更多轮次才能确认，不能凭单轮定论。**
本批数据中，**每个配置只有 1 次整轮测量**（唯一例外是 0.6B·16K·f16 有 2 次），
**不足以做统计显著性判断**。

**（c）c1 上的吞吐异常（与整体趋势相反）—— 标为疑似噪声，需复测。**

- `ctx16k-q80-06b-r2` 组对比里，q8_0 在 **c1 的吞吐比 f16 高 35.1%**（128.1 → 173.1 tok/s）；
- 同一次对比里 c4、c10 的吞吐却是 **−14.3%、−21.8%**；
- 1.7B 组（对比 4）也出现同样形态：c1 吞吐 **+23.2%**，而 c4 为 −27.6%。

**这个方向和"KV 降精度会变慢"的整体趋势相反，且只出现在 c1 档。**
在 c1 档下服务端没有排队，吞吐受单请求生成速度支配，理论上只应该由 kernel 效率决定；
q8_0 的 KV 反量化通常**不会更快**。因此合理判断是：

> **c1 的吞吐差异属于噪声/单次测量波动，不能得出"q8_0 更快"的结论，需要复测确认。**

**（d）由此得到的取舍：**

| 结论 | 强度 |
| --- | --- |
| 上下文 16K→32K **显著增加显存**（+51% / +38.5%） | **强**（两次独立对比都是同方向，且幅度远超波动） |

| **c1 吞吐在 q8_0 下更高** | **不成立**，疑为噪声，需复测 |

### 8.4 ⚠️ 方法论：检测手段本身错了会误导结论

这一段记录的是**检查流程的缺陷**，不是模型的问题。它值得写进报告，因为
**"报出来的失败"里有假阳性时，结论会完全反过来**。

**（a）编程输出：把整篇输出当 Python 编译 → C01 被判"语法失败"。**

`tests/core/test_08_output_code.py` 最初的实现是"剥掉首尾围栏，把中间全部当代码"送 `py_compile`。
于是：

- **C01** 题目要的是"**代码审查报告**"（问题定位与最小复现，输出本来就是说明文字，没有代码围栏），
  整篇文字被送进 `py_compile` → **必然报语法错**。9 次运行里 **6 次**被判"语法失败"——**全是假阳性**。
- **P04**（程序设计方案，说明 + 片段）同理。

修法（`evaluate_code_tasks.py` 与已修正的 `test_08`）：**只编译 markdown 围栏里的代码**；
没有围栏就如实说"**没提取到代码**"，而不是报"语法错"。因为这两件事性质完全不同：

| 判定 | 含义 | 对场景的影响 |
| --- | --- | --- |
| `code_syntax`（语法错） | 模型写出来的代码有问题 | 要换更强的模型 / 改提示词 |
| `no_code`（没给代码） | 模型**没按要求给代码** | 对 `code` 任务是**真发现**（C01 9 次里 6 次只给了文字分析） |

修正后的真实结论：**C01 的 6 次 `no_code` 是"只给了文字分析、没给可运行的复现代码"**，
而 `code_syntax` 实际只有 **1 次**（`ctx16k-q80-17b-r1`，`IndentationError: unexpected indent`）。

**（b）办公输出：用正则判"是否用了旧会议决定" → 两次误报。**

最初想自动判"有没有把旧会议的决定当成现行决定"，做法是找输出里有没有出现旧日期。
**两次都误报** —— 原因很简单：

> "**原定 X 改为 Y**"这种**正确**的表述**必然**会提到旧值 X。
> 任何"出现旧值就算错"的规则，都会把**正确仲裁**判成错误。

最后**放弃自动判定**，只做**正向核对**（现行日期是不是 10 月 20 日、有没有交代变更），
**语义判断留给人**。这也是 §8.2 那张"逐运行 D02 措辞表"必须人工整理的原因。
（用于复核那次误报的脚本留在仓库里：`verify_d01_stale.py`，
它把输出里所有 `10 月 16 日` 的位置连同上下文打出来，供人肉判断。）

**（c）这两件事的共同教训**：

> **自动判定的"独立来源"必须是客观可核对的量**（能不能编译、日期是否等于 10 月 20 日、条款编号是否出现），
> **不能是需要理解语义才能判断的量**（"这句话是不是把旧值当现值"）。
> 用语义规则去自动判定语义问题，产出的失败数字**看起来很像证据，实际上不可用**。

### 8.5 办公任务为什么必须人工核对

`tests/README.md` §二 已明确记录 `test_07_output_office.py` **未做**，
理由就是"**办公输出检查需人工判定为主**"。本报告的 §8.1 / §8.2 就是这次人工核对的结果：

- **机器能做的**：客观项的正向核对（日期是不是 10 月 20 日、条款编号有没有出现、格式要素齐不齐）→
  结构化落在 `results/office-eval.json`。
- **机器不能做的**：输出里的表述**是否正确理解**了资料（例如"原定 10 月 16 日改为 10 月 20 日"
  是正确仲裁还是照抄旧值；"平均处理耗时口径待确认"是否真的在资料里是未决项）→
  只能人工看原文，见 §8.2。

## 9. 错误记录与服务恢复

### 9.1 机制

| 组成 | 位置 | 说明 |
| --- | --- | --- |
| 后台监测 | `src/control/service_watch.py` | 后台线程，默认每 **3.0 秒**探一次 `/health`（`poll_interval_s`） |
| 防抖 | 同上 | **连续失败 2 次**才算"真的掉了"（`fail_threshold`），避免偶尔一次探测失败就动手 |
| 服务页开关 | `src/web/` 服务页 | **默认关**（`enabled: False`）—— 会真的动进程的操作不该默认开 |
| 冷却 | 同上 | 两次重启之间至少隔 **20 秒**（`cooldown_s`），避免"刚起来还没加载完又被判掉线" |
| 单次上限 | 同上 | 同一次测试最多重启 **2 次**（`max_restarts_per_run`）；起来就挂说明不是偶发问题，反复重启只会掩盖它 |
| 就绪超时 | 同上 | 等就绪上限 **90 秒**（`ready_timeout_s`） |
| **总闸** | 同上 | **只在【测试运行中】或【测试刚结束的 90 秒宽限期内】才自动重启；其余时间只提示不动作** |
| 事件时间线 | `src/logs/service-events.jsonl` | 每次动作/不动作都记一条（时间、原因、耗时、结果） |
| 运行目录内的启动记录 | `results/<运行编号>/service-starts.jsonl` | 该轮测试期间"服务被拉起"的事实记录（**这是判断这一轮完不完整的直接依据**） |

### 9.2 核心规则：为什么"只在测试运行中才动作"

**这条规则是本模块最要紧的设计，而且它是被一次失败逼出来的。**

最初做过一版"服务掉了就自动重启"，结果**有害**，最后整个移除了。原因是它分不清两种情况：

```
① 服务真的崩了                    → 该救
② 有人正在【有意】重启服务         → 不该救
   （serve.sh model 的语义就是先停后起，中间约 3 秒没监听）
```

第 ② 种在监测器眼里**和崩溃一模一样**，于是它每次都去"救"，
而"救"的过程（停进程 + 启动 + 等就绪）**自己又制造一次空窗** —— 服务被反复停起。
实测表现：手动使用时服务很稳，一跑测试脚本就频繁掉线。

**解法不是去"分辨"那次掉线是有意还是意外，而是换一个维度：只在明确的时间窗内动作。**

```
测试在跑   → 服务掉了说明是意外，救它
其余时间   → 只提示，绝不动手（多半是有人故意停的 / 正在换模型）
```

这条规则同时满足了另一个要求："如果在跑测试之前模型就掉了，那只能提示，不会有动作。"
事件时间线里因此存在两种事件类型：`noticed_only`（只提示，附 `why_no_action` 说明）
与 `give_up`（达到单次重启上限，交给人处理）—— 实例见 `src/logs/service-events.jsonl`。

**⚠️ 一个必须有宽限期的坑（也是实测踩出来的）**：
服务在测试**中途**挂掉时，剩下的请求会很快集体失败，测试程序于是**提前跑完退出**；
等监测器下一次探活时，`bench_runner.active()` 已经返回 `None` ——
按总闸规则判成"没有测试在跑，只提示不动作"，**眼睁睁看着不去救**。
因此加了 90 秒宽限期：只要**刚刚**还有测试在跑，就仍认为这次掉线是测试期间的意外。
宽限期不能太长 —— 否则"人跑完测试后手工停服务"也会被当成意外而自动拉起。

### 10.2 有效的优化

1. **上下文 16K → 32K（0.6B）：c10 档 TTFT −20.3%、吞吐 +6.4%，显存 +51%。**
   代价换来的是 10 并发下"少等 0.5 秒"和更高的吞吐，且显存仍在 67% —— **这是本阶段唯一净收益明确的改动**。
2. **KV 精度 f16 → q8_0：显存 −20%。**
   在"必须先腾出显存"的场合（例如要换 1.7B）这是唯一可行的手段，
   但**代价是 c4/c10 吞吐下降 14%~22%**，因此**不作为默认**。
3. **`-v` + `--cache-ram 0`**：这不是性能优化，而是**可验证性的前提** ——
   没有 `-v` 就没有 `CUDA0 KV buffer size` 这一行，KV 容量的口径就没法证明。

### 10.3 发现的问题

1. **slot 数 4 与并发档 10 不匹配**：c10 档下 6 个请求排队，TTFT 中位数涨到 c1 的约 98 倍。
   这是本机最大的可用性瓶颈。
2. **`max_tokens = 2048` 对 1.7B 偏小**：P04 有 6/9 次、C01 有 3/9 次撞上限。
   "换更大的模型"反而先撞输出上限 —— **先解决配置，再谈模型**。
3. **c10 档 P95 是中位数的 5~12 倍**：说明 c10 有一批请求在等十几到二十几秒，
   只看中位数会严重低估用户的真实体验。
4. **c1 吞吐在 q8_0 下反常升高 35%**：与整体趋势相反，**未解释，疑为噪声，需复测**。
5. **样本量不足**：上下文组与 KV 组各只有 2 轮 0.6B 数据，1.7B 各 1 轮，**不足以做统计显著性判断**。
6. **模型输出层面的两处真实缺陷**：D02 有 3/9 次漏"已批准 vs 备选"的区分；
   D03 有 5/9 次漏 D05 条款，且 0.6B 出现过条款编号张冠李戴（A03/B03 混淆）。
7. **检查流程自身出过两次错**（§8.4）：整篇输出当代码编译造成 6 次假阳性；
   正则判旧会议决定两次误报。**这两件事的教训是：自动判定只能用客观可核对的量。**

| 测试程序（`tests/core/run_bench.py`）、客户端（`src/bench/client.py`） | AI 起草 | 人确定了**成功率口径**（只有 `finish_reason` 或 `[DONE]` 才算成功）；人发现并纠正了**吞吐窗口用错了时间基准**（曾用逐请求相对时间戳推算，把吞吐高估约 12 倍，改成墙钟后正确） |
| 测试套件（`tests/`，9 个，约 2100 项断言） | AI 起草 | 人坚持每个测试必须有**独立来源**（见下 §11.3），否则测试就是"拿被测代码验证它自己" |
| 本报告的数据核对 | AI 抽取 | 人逐项核对运行编号与出处；**下面三件事是人拦下来的** |

**三件必须如实记录的事（AI 参与但判断错了，由人纠正）：**

**（1）AI 写的"自动重启"第一版是有害的，被移除后又用"总闸"重做。**

第一版逻辑是"服务掉了就自动重启"。它分不清"真崩"和"有人正在有意重启"，
于是每次 `serve.sh model`（先停后起，中间约 3 秒没监听）都被它当成崩溃去"救"，
而"救"的过程又制造一次空窗 —— **服务被反复停起，一跑测试就频繁掉线**。
人的判断：**移除整个功能**，并把 `test_05_errors.py` / `test_06_recovery.sh` 一并删掉
（理由：它们依赖这套有害功能）。
后来重做时换了思路：**不再试图分辨"有意还是意外"，改成"只在明确的时间窗内动作"** ——
只在测试运行中或刚结束的 90 秒宽限期内才重启，其余时间只提示。
这一版才是现在 `src/control/service_watch.py` 的样子，**开关默认关**。
（完整经过写在 `tests/README.md` §二"为什么移除 test_05 / test_06"。）

**（2）AI 的编程输出检测脚本把整篇输出当 Python 编译，造成 6 次假阳性。**

`test_08_output_code.py` 的初版把模型输出的**整篇文本**送 `py_compile`，
于是 C01（题目要的是代码审查报告，输出本来就是文字）被判"语法失败" ——
**6/9 次全是假阳性**。人的判断：
**"没给代码"和"语法错"是两件性质完全不同的事，不能报成同一个结论**。
重写为**只编译 markdown 围栏里的代码**（`evaluate_code_tasks.py`），
没有围栏就如实记 `no_code`。修正后 C01 的真实判定是 **6 次没给代码、1 次语法错、2 次通过**。

**（3）AI 写的正则判定"是否用了旧会议决定"，两次都误报。**

规则是"出现旧日期就算错"。人的判断：
**"原定 X 改为 Y"这种正确表述必然提到旧值 X**，任何这样的规则都会把正确仲裁判成错误。
于是**放弃自动判定**，改成只做正向核对（现行日期是不是 10 月 20 日、有没有交代变更），
语义判断留给人（复核脚本 `verify_d01_stale.py` 只负责把相关片段打出来供人看）。

**这三件事的共同点**：AI 产出的东西**看起来能跑、也有输出**，
但它的**判定口径**是错的 —— 而错误口径产出的数字**长得和证据一样**。
人在这里起的作用不是"改代码"，而是**判断这个口径对不对**。

### 11.3 代码、性能数据和输出的核验方法

**核验的核心原则：每个断言都要有一个【独立来源】。拿被测代码验证它自己叫循环论证，永远通过。**

| 断言 | 独立来源 | 强度 |
| --- | --- | --- |
| `ttft_ms == (t_first − t_submit) × 1000` | 记录里的**原始时间戳** + 手算 | 强 |
| `summary` 的中位数 == 逐请求重算 | `_testlib.py` 里**另写的中位数** | 强 |
| `summary` 的 P95 == 逐请求重算 | `_testlib.py` 里**另写的线性插值** | 强 |
| 吞吐 == Σ(output_tokens) / 墙钟 | 逐请求记录 + 墙钟字段 | 强 |
| `output_tokens` 不是"数块数"得来的 | **服务端 `timings.predicted_n`** | 强 |
| `prompt_n_computed + cache_hit == prompt_tokens` | 服务端**恒等式** | 强 |
| 每条输入 ≤ 50,000 token（题目上限） | 题目规定的上限 | 强 |
| 编程输出可编译可执行 | **真跑一遍**（存文件 → `py_compile` → `import` → 喂边界输入） | 最强 |
| 前端有 6 项展示能力 | **题目原文列的 6 项** | 强 |
| 写入路径被 `.gitignore` 覆盖 | `git check-ignore`（**外部工具**） | 强 |

**三类数据的核验方式：**

| 数据 | 核验方式 |
| --- | --- |
| **代码** | ① `tests/run_all.sh` 跑 9 个测试、约 2100 项断言，退出码 = 失败个数；② 编程输出**真的编译并执行**；③ 文档里的每个数字都要能在 `results/` 里找到出处 |
| **性能数据** | ① 指标**另写一套算法重算**并比对（`_testlib.py`）；② 单变量对比表由 `report_data.py` 从 `summary.json` **程序化生成**，不手抄；③ 每次运行前校验"配置模型 == 实际加载模型"，不一致直接终止 |
| **模型输出** | ① 编程：**真编译、真 import、真跑边界用例**，并**先查截断再查语法**；② 办公：客观项正向核对，语义项人工；③ **任何"失败"数字都要先排除假阳性**（§8.4） |

**AI 参与部分的核验**：本报告里所有百分比与指标都是从
`results/report-data.txt`（由 `report_data.py` 从 `summary.json` 程序化导出）逐条抄录，
**没有一处是人工计算的**；运行编号与数据路径逐条标注，读者可直接回溯核对。
